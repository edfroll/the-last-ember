- Оттенки моделей: `custom_model_data.colors` = [тело, глаза]; текстура глаз белая, цвет задаёт оттенок.
- `#minecraft:dirt` в 26.3 — только dirt/coarse/rooted; для «копается в земле» — свой тег `#last_ember:diggable`.
- Звук из пака без регистрации на сервере отправляется только в 16 × громкость блоков. Чтобы слышать голос дальше, поднимать громкость, а не `attenuation_distance` (см. T-018 в `CLAUDE.md`).

### Окружение и инструменты агента

- **Сервер запускать фоновой задачей агента** (`run_in_background`) или `tools/server.sh start > log &`. Если запускать foreground-командой с ожиданием, агент упирается в таймаут. Повторный `start` при уже запущенном сервере падает с `session.lock: already locked` — это не авария: проверить `tools/server.sh rcon list`.
- **Клиент кэширует ресурс-пак по sha1.** После смены моделей или текстур: `tools/server.sh stop` → `start` (он пакует пак и пишет новый sha1) → перезапустить клиенты. Без рестарта новые модели не появятся или станут розово-чёрными.
- **`http.server 8765` переживает остановку сервера.** После переноса папки проекта старый процесс раздавал пак из старого пути — его надо убить: `pkill -f "http.server 8765"`, затем `start` поднимет новый.
- Если правка Python-генератора через вставку `;` попадает после комментария `#` в той же строке, остаток строки молча становится комментарием (так однажды пропали 5 моделей варга). После генерации проверять, что все файлы на месте.
- Кадры тестов: PNG 2560×1440 по ~2 МБ. Перед коммитом сжимать: `magick f.png -resize 1280x -quality 78 f.jpg`. Листы-сводки — `magick montage`.

## 6. Экономия контекста (решение Эдварда, 19.11.2026)

Почти весь расход лимита в долгих сессиях — перечитывание накопленного контекста (T-025 съел около 180M токенов), а не сами проверки. Поэтому:
- Длинные логи (сервер, бот-ходок, генераторы, `rebuild.sh`, тесты) **не выводить в контекст целиком**: писать в файл, например `cmd > server/debug/<имя>.log 2>&1`, и смотреть только `tail -n 30` или `grep -nE 'ERROR|WARN|Exception|Traceback|FAIL'`.
- Запускать в фоне, ждать завершения, читать только итоговую строку и хвост.
- Файлы и кадры читать точечно (`offset`/`limit`, диапазон строк), а не целиком.
- **Проверки при этом не урезать:** бот-ходок, живые клиенты Cam/Cam2 и кадры остаются обязательными — они находили непроходимость, которую не видят RCON-тесты.
- Доработка по приёмке Штаба делается новой короткой сессией (отдельный тред), а не продолжением старого: длинный контекст старого треда дорого перечитывать.

## 7. Кеш мира (решение Эдварда, 20.11.2026)

Сборка тест-мира с нуля в облаке — 17,4 мин (генерация чанков 4,6; скан 0,8; Приют и Кольцевая гора 2,6; рамка Р1 и места ~10). Каждая задача пересобирала мир заново. Теперь мир главной ветки лежит в архиве, задача пересобирает только то, что поменяла.

**Где лежит.** Ветка `world-cache` этого репо: один коммит без истории (перезаписывается), в нём `manifest.json` и два архива частями по 95 МБ (лимит GitHub на файл — 100 МБ):
- `gen` — сгенерированные чанки (`tick freeze`, датапак не работал) + `server/build/r1/nat.bin`. Ключ — сид, серверный jar, worldgen датапака, область pregen.
- `final` — готовый мир **до первого старта** (состояние датапака чистое: костры, торговцы, статуи строятся при старте, как в обычной сборке) + `server/build/r1/*.bin/json/npz/txt` (входы шагов мест) + `snap/<место>/` — чанки коробки каждого места (region, entities, poi) такими, какими они были прямо перед его шагом в `r1_apply.sh` (снимает `tools/terrain.sh`, когда сканирует `<место>_pre.bin` при заданном `LE_SNAPDIR`).
Ветка доступна обоим аккаунтам через обычный git (папка проекта корп-билдеру не видна, release из облака создать нечем — нет токена API). Облачный клон берёт только `main` и рабочую ветку, так что архив не скачивается, пока его не попросят.

**Пометка в задаче.** Штаб пишет в шапке задачи строку `Сборка: из архива` (по умолчанию, если строки нет) или `Сборка: с нуля` (контрольная: раз в несколько задач и обязательно перед релизом).

**Начало задачи (из архива):**
1. `python3 tools/world_cache.py fetch` (~240 МБ; сверяет sha256 каждого архива с манифестом) → `python3 tools/world_cache.py status`.
2. `status` сравнивает входы мира между коммитом архива и рабочим деревом и называет режим:
   - `final` — ничего не менялось: `python3 tools/world_cache.py restore final && tools/build/rebuild.sh --start-only` (~0,5 мин + клиент);
   - `redo <места>` — поменялись только файлы этих мест (`tools/build/r1_<место>.py`, `<место>_*.py`) или их строки в `r1_apply.sh`, либо в `r1_apply.sh` появилось новое место: `python3 tools/world_cache.py redo <места>` — берёт `final`, возвращает чанки коробки места из `snap/` (старая постройка исчезает целиком — генератору не нужно ничего вычищать), запускает шаг места и хвост `r1_apply.sh` (биомы, барьеры, `sync`), затем `tools/build/rebuild.sh --start-only`. Новое место без снимка просто строится: его коробка в архиве нетронута. Время: шаг места (Круг ~1 мин, лабиринт ~4, сад ~0,5, топи ~1, кладбище ~0,3) + хвост 0,8 мин. Шаг места можно вынести в свой скрипт `tools/build/<место>_step.sh` (как T-027): его правки считаются правками места, имя места — по скану `<место>_pre.bin`, другие имена — из `r1_check.py places a+b`;
   - `gen` — поменялись рамка, Приют, общие инструменты (`lib.py`, `Terrain.java`, `terrain.sh`…), биомы, костры, ворота: `tools/build/rebuild.sh --cache` (всё после генерации чанков, 12,4 мин);
   - `scratch` — поменялись сид, jar, worldgen датапака или область pregen: `tools/build/rebuild.sh` (17,4 мин).
   Правки только датапака (функции), ресурс-пака, тестов, документов мир до старта не меняют — режим `final`, датапак всё равно синхронизируется при старте.
3. Во время работы над своим местом — снова `redo <место>` после каждой правки генератора (это и есть «пересборка своего региона»; старые блоки места не остаются).
4. **Проверки не урезаются:** RCON-тесты, бот-ходок по **всему** маршруту задачи, кадры — как раньше, на мире из кеша.

**После слияния PR в `main`** (делает билдер следующей задачи, если архив старше `main` и `status` не `final`): собрать мир `main` нужным режимом (`rebuild.sh`/`--cache` сами пишут `server/cache/gen|final.tar.gz` и манифест; после `redo` — `python3 tools/world_cache.py save final`), затем `python3 tools/world_cache.py push`. `push` отказывается, если мир собран из незакоммиченных входов, если коммит мира не входит в `origin/main` или если в ветке лежит мир более нового коммита (через `--force-with-lease`). Контрольная сборка с нуля тоже заканчивается `push` — так обновляется и `gen`.

**Сессия без права пуша** (облачный тред без подключённого репо): `python3 tools/world_cache.py push --bundle <папка>` — те же проверки (нет грязных входов, коммит мира в `origin/main`, архив на origin не новее) и тот же коммит ветки `world-cache` из `server/cache/gen|final.tar.gz` и манифеста, но вместо `git push` — `git bundle` этой ветки, нарезанный на `<папка>/world-cache.bundle.NN` (≤ 95 МБ), и `world-cache.txt`: коммит, lease (текущий `world-cache` на origin; пусто — ветки ещё нет), sha256 целого бандла. Части пересылаются Эдварду, локальная сессия выкладывает:
```bash
cat world-cache.bundle.?? > world-cache.bundle   # сверить sha256 с world-cache.txt
git fetch world-cache.bundle world-cache:world-cache-new
git push --force-with-lease=refs/heads/world-cache:<lease> origin world-cache-new:refs/heads/world-cache
python3 tools/world_cache.py fetch && python3 tools/world_cache.py status
```
Если за это время кто-то обновил `world-cache`, lease не совпадёт и push откажет — тогда архив пересобирают заново от нового.

**Ограничения.** Сборка с нуля не обязана совпадать с прошлой сборкой с нуля блок в блок (ванильная генерация деревьев на стыках чанков, см.
